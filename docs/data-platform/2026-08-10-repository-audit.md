# 数据平台仓库审计

状态：第一阶段审计完成，设计待评审
日期：2026-08-10
审计范围：仓库结构、数据对象、文件契约、版本策略、写入安全性、测试与产品规划

## 1. 当前技术形态

Spike-Trace 当前是 Python 3.10+ 的本地 CLI 与模块化单体：

- 没有数据库、HTTP API、账户系统或前端工程。
- 运行时依赖为 NumPy、OpenCV、PyTorch、TorchVision；可选接入 Ultralytics。
- 业务数据和运行产物保存在 CSV、JSON、PyTorch checkpoint、视频与工作簿文件中。
- `data/annotations/` 中的 CSV/JSON 可进入版本控制；视频、权重、训练目录和大部分输出默认忽略。
- 当前只有一场真实比赛和一份全部属于 `train` 的 90 条标注清单，尚无独立比赛验证集。

因此，现状不是“已有数据库但缺页面”，而是“已有可复现文件流水线，需要在不破坏契约的前提下引入正式事实库”。

## 2. 当前数据对象

### 2.1 内存领域对象

`src/spiketrace/domain.py` 目前定义四类对象：

| 对象 | 当前字段 | 审计结论 |
| --- | --- | --- |
| `AnnotationRecord` | 视频路径、起止秒数、标签、split、半场、号码、裁剪 | 可作为标注导入 DTO，不足以表达稳定 ID、版本和来源 |
| `VideoMetadata` | 路径、帧率、帧数、宽高、时长 | 缺少内容哈希、编解码、文件大小、导入状态和工作区归属 |
| `ActionWindow` | 起止秒数、动作、置信度 | 适合作为模型原始证据，不应直接成为已确认比赛事实 |
| `ActionEvent` | 视频/事件 ID、毫秒时间、动作、置信度、半场、号码、状态、模型版本、来源 | 已为长期事件契约预留身份字段，但缺少工作区、比赛、修订、模型产物和审核谱系 |

### 2.2 文件资产

当前仓库中的主要资产如下：

| 资产 | 用途 | 当前版本/锁定机制 |
| --- | --- | --- |
| 标注 manifest CSV | 训练窗口与人工结果 | 稳定列；UTF-8 BOM；CRLF；按整场视频隔离 split |
| 比赛 JSON | 比赛、视频、半场、清单、基线和批次摘要 | 没有顶层 `format_version`；内容结构随项目演进 |
| 二次复核规格 JSON | 指定待复核记录和建议操作 | `format_version = 1`；按 manifest 文件名绑定 |
| 二次复核结果 JSON | 人工确认与完整来源快照 | `format_version = 1`；逐字段核对来源 |
| 补标批次规格 JSON | 锁定来源清单、回合和工作簿 | `format_version = 1`；manifest/workbook SHA-256 |
| 补标结果 JSON | 规范化的人工动作、删除快照和摘要 | `format_version = 1`；输入/输出哈希和单元格来源 |
| 训练配置与指标 JSON | 训练参数、manifest 摘要、历史指标 | 标签契约版本写入配置；报告本身无独立顶层格式版本 |
| PyTorch checkpoint | 模型权重和可复现参数 | `CHECKPOINT_FORMAT_VERSION = 1`；标签契约版本为 2 |
| 预训练评估 JSON/CSV | 权重、环境、逐窗证据、严格/兼容指标 | `format_version = 1`；权重 SHA-256 |
| 推理 `events.json/events.csv` | 最终事件与原始滑窗 | JSON `format_version = 1`；包含模型版本和设置 |
| 视频与工作簿 | 原始媒体和人工填写界面 | 路径引用；部分工作簿用 SHA-256 锁定 |

### 2.3 标注 CSV 现状

必需列：

```text
video_path,start_seconds,end_seconds,label,split
```

当前常用可选列：

```text
team_side,player_number,crop_x1,crop_y1,crop_x2,crop_y2,review_status,notes
```

现有校验包括：

- 未知动作标签、未知 split、非有限时间、负时间和 `start >= end` 被拒绝。
- 四个裁剪坐标必须全部提供或全部为空，且范围合法。
- 同一视频不能出现在多个数据集 split。
- 默认要求视频文件存在；跨设备结构校验可显式关闭。
- 复核读取会拒绝表头之外的额外单元格。

现有风险：

- 记录身份依赖行号或位置，没有稳定的 `annotation_id`。
- `video_path` 同时承担展示、定位和关联身份，路径移动会改变含义。
- 标注行可以带号码，但没有 `player_id` 或 roster 约束。
- 文件名和 SHA-256 承担了部分版本图职责，无法高效查询完整谱系。
- CSV 没有显式的 manifest 契约版本；标签版本只在训练侧记录。

## 3. 当前版本和审计策略

### 3.1 已有优点

- 七类动作契约使用 `ACTION_LABEL_SCHEMA_VERSION = 2`，旧六类 checkpoint 仍按自身标签加载。
- checkpoint、复核规格、复核结果、预训练评估和事件 JSON 都有独立格式版本。
- 补标规格以来源 manifest SHA-256 锁定输入，补标结果保存输入、工作簿和输出哈希。
- 原清单不被覆盖，每轮复核/补标生成新清单。
- 二次复核保存完整来源快照，任何微小时间或元数据变化都会拒绝应用。
- 复核输出先写入临时文件，重新加载验证成功后再原子替换。
- 标注 CSV 的 Git 属性固定 CRLF，避免跨设备换行导致来源哈希变化。

这些做法应迁移为正式数据平台的不可变版本、乐观并发和来源谱系，而不是在导入数据库时丢弃。

### 3.2 主要缺口

- 比赛 JSON、训练报告和若干人工批次结构没有统一 schema 注册或迁移策略。
- `model_version` 是调用方字符串，尚未与实际权重 SHA-256、代码版本和配置形成唯一模型产物 ID。
- 事件的 `status` 只有字符串，没有保存每次预测、修正与确认的独立修订。
- 当前统计主要是 manifest 摘要和模型指标，没有球员统计事实、公式版本或来源事件版本。
- 没有统一审计主体；现有 `confirmation_source: user` 无法指向具体账户或本机身份。
- 没有跨实体事务，比赛 JSON、manifest、评估摘要之间可能出现引用已更新但目标未同步的状态。

## 4. 当前写入与错误边界

### 4.1 已有安全措施

- 清单、规格和结果禁止同路径覆盖。
- 复核确认必须完整、唯一且按规格顺序。
- 输出 manifest 重新加载后才替换目标。
- checkpoint 通过临时文件后原子替换。
- 错误类型区分 manifest、review、checkpoint 和通用 Spike-Trace 错误。

### 4.2 需要补齐

- 训练配置、指标、预训练评估和事件 JSON 目前直接写目标文件，缺少统一原子写入器。
- 推理 JSON 与 CSV 是两次独立写入，失败时可能只产生一半产物。
- 文件目录没有统一锁或单写者规则，多个进程可能写入同一目标。
- 路径解析大量使用绝对路径，未来 API 不应把本机绝对路径暴露给前端或导出消费者。
- 大文件去重、引用计数、垃圾回收、磁盘不足与断点恢复尚未定义。

## 5. API 与用户界面现状

- 当前公共入口全部是 CLI 子命令：清单校验、视频检查、训练、推理、预训练评估、复核队列生成和复核应用。
- Python 模块函数直接接收路径并返回字典，没有应用服务、仓储接口或稳定的错误响应 envelope。
- 没有账户、工作区、成员、偏好、存储用量、导入任务或导出任务页面。
- 产品规划明确把完整桌面/Web UI、账号、数据库和球员档案后置，但长期方向已经确认本地优先与 SQLite。

## 6. 测试审计

现有测试覆盖：

- 标注清单解析、标签、裁剪、时间和 split 泄漏。
- checkpoint 标签契约和旧六类兼容。
- 指标、事件合并、视频窗口。
- 预训练标签归一化、评估产物和严格/兼容指标。
- 二次复核的来源快照、乱序/重复/额外结果、原子替换和真实规格。
- 当前真实比赛半场段、补标批次与输出清单哈希一致性。

缺少的数据平台测试面：

- 数据库迁移、外键、工作区隔离和并发。
- 同一资产重复导入的幂等性和内容去重。
- 不可变版本、父版本、当前指针和乐观并发。
- JSON/CSV 往返、冲突策略和部分失败回滚。
- 统计投影可重算性及公式版本。
- 账户/成员角色与 API 资源授权。

审计时尝试运行 `python -m unittest discover -s tests -v`，但当前 PowerShell 的 `python.exe` 指向 Microsoft Store 应用别名，未找到可用解释器。因此本阶段只有静态契约审计，没有新的运行时测试结果。

## 7. 对数据平台设计的直接约束

1. 保留本地优先和模块化单体，不让数据库迫使现有模型模块变成网络服务。
2. 数据库只存结构化事实、版本、路径引用和哈希；视频、模型和证据文件仍在文件系统。
3. 当前 CSV/JSON 是迁移与兼容入口，不能简单弃用。
4. 导入必须保存原始文件哈希、来源文件名、契约版本和完整错误报告。
5. 标注版本、事件修订和统计快照必须可追溯，不允许“导入后只剩当前值”。
6. 数据集 split 继续按完整比赛隔离，数据库层增加可执行约束和验证器。
7. 模型评估必须绑定确切的模型资产、标注版本、配置、代码版本和设备环境。
8. 球员统计必须从已确认事件和 roster 归属重算，不能把 CSV 汇总当作唯一事实。
9. 所有表和 API 资源必须带 `workspace_id` 或通过父实体强制解析到工作区。
10. 账户/工作区页面不能决定全局导航或分析/标注工作台的信息架构。
