# Spike-Trace MVP 产品工作流设计

状态：第一阶段审计与设计草案

更新时间：2026-08-10

## 1. 目标与边界

本文档基于当前仓库基线，定义 Spike-Trace 的 MVP 产品工作流。第一阶段仅做审计与设计，不改运行时代码，也不决定号码识别或持久化存储的内部实现。

这版 MVP 已确认的产品方向是：

- 把现有能力组织成一个清晰的分析工作流。
- 覆盖视频导入、标注复核、模型评估、球员统计和 CSV/JSON 导出。
- 让模型产物、复核结果和导出结果都可追溯。
- 把高级身份识别、长期球员档案和正式数据库内部实现留给后续 Lane 或后续阶段。

## 2. 审计结论

当前仓库是一个 Python CLI 项目，还不是完成态的 Web 或桌面产品。基线里已经有 MVP UI 需要包起来的核心机器流程：

- `inspect-video`：读取视频元数据并验证解码支持。
- `validate-manifest`：验证标注 CSV 输入。
- `train`：训练动作分类器。
- `infer`：对完整视频做滑窗推理并合并窗口为事件。
- `evaluate-pretrained`：用 Spike-Trace 标签契约评估外部预训练权重。
- `prepare-review` 和 `apply-review`：生成并应用可审计的人工复核批次。

现有数据契约已经定义了 MVP 的骨架：

- 标注契约：`video_path`、`start_seconds`、`end_seconds`、`label`、`split`，以及可选的 `team_side`、`player_number` 和 crop。
- 事件契约：`video_id`、`event_id`、`start_ms`、`end_ms`、`action`、`confidence`、可选 `team_side`、可选 `player_number`、`status`、`model_version`、`source`。
- 导出产物：`events.json` 和 `events.csv`。
- 评估产物：accuracy、macro F1、逐类指标、混淆矩阵。
- 复核操作：`keep`、`relabel`、`move_window`、`add_window`，并且要做源快照校验和非破坏式输出。

当前严格动作集是：

- `background`
- `serve`
- `receive`
- `set`
- `attack`
- `block`
- `dig`

仓库当前还没有：

- 浏览器或桌面 UI
- 正式的应用状态模型
- 持久化任务注册表或数据库
- 自动球衣号码分配
- 完整球员档案或跨比赛报表界面

## 3. 产品形态建议

MVP 可以考虑三种产品形态：

1. CLI 优先的辅助壳：设计成本最低，但可发现性和复核体验都弱。
2. 分析任务工作台：把当前 CLI 流程组织成一个有明确产物和门禁的引导式工作区。
3. 完整排球分析平台：从第一版就包含数据库、阵容中心、报表、档案和丰富分析。

推荐选择：方案 2，分析任务工作台。

原因：

- 它符合仓库当前成熟度。
- 它能把现有命令和文件契约变成可用的操作流程，而不是假装产品已经比现实更大。
- 它能给后续 Lane 提供稳定的工作流和产物边界。
- 它避免过早承诺存储、OCR 或身份识别的内部实现。

## 4. MVP 工作流

MVP 应围绕一个分析任务组织。

每个任务代表一场比赛视频或一个可复核的分析包，并按以下步骤推进：

1. 导入视频和源标注。
2. 校验元数据和标注清单完整性。
3. 准备或查看复核队列。
4. 运行或查看模型输出。
5. 复核修正事件。
6. 查看评估结果和质量警告。
7. 查看事件账本和球员统计。
8. 导出 CSV/JSON 产物。

推荐的顶层流程：

```mermaid
flowchart LR
    A["分析首页"] --> B["导入与设置"]
    B --> C["复核工作区"]
    C --> D["评估报告"]
    D --> E["事件与球员统计"]
    E --> F["导出中心"]
```

这条流程故意做成首用时尽量线性，但每个完成步骤都应能从同一个任务中重新进入。

## 5. 页面与用户流程

### 5.1 分析首页

目的：

- 展示分析任务、当前状态、最新产物时间和失败状态。
- 从本地视频和可选标注创建新任务。
- 直接回到上一个未完成步骤。

必须展示：

- 任务名
- 源视频名
- 当前工作流状态
- 上一个成功阶段
- 是否已有复核、评估或导出产物

### 5.2 导入与设置

目的：

- 收集源视频、可选标注清单、目标队伍上下文和基础备注。
- 在进入后续步骤前完成视频检查和标注校验。

必须展示：

- 视频元数据预览
- 标注校验结果
- 标签覆盖情况
- split 汇总
- 缺失或非法字段错误
- 可选 crop 和 team-side 作为导入元数据，而不是强行要求的新 UI 输入

继续门禁：

- 视频可解码。
- 若提供标注清单，则格式有效。
- 任务可以持有它的源产物稳定引用。

### 5.3 复核工作区

目的：

- 让人工复核成为 MVP 里最重要的可信修正中心。
- 支持人工查看源标签、预测事件或复核请求，并且不覆盖源文件。

推荐布局：

- 视频播放器
- 时间轴，显示当前窗口和修正后的事件跨度
- 事件或队列表
- 右侧详情面板，显示所选条目的元数据和备注

核心动作：

- 接受当前条目
- 改标签
- 调整时间窗
- 新增遗漏窗口
- 记录复核备注

必须保留：

- 源快照
- 复核操作
- 确认后的动作
- 确认后的时间
- 复核备注
- 输出产物引用

### 5.4 评估报告

目的：

- 把模型质量讲清楚，足以支撑 go / no-go 判断。
- 严格区分 Spike-Trace 自身的指标和外部预训练模型的兼容性指标。

必须展示：

- Accuracy
- Macro F1
- 每类 Precision / Recall / F1
- 混淆矩阵
- 产生结果的具体产物或 checkpoint
- 当评估不来自独立比赛时的范围警告

重要警告规则：

如果训练数据和评估数据来自同一场比赛，报告必须明确说明结果只属于 baseline，不是可部署证据。

### 5.5 事件与球员统计

目的：

- 把模型输出和复核输出变成可读的事件账本和第一版统计视图。

事件视图必须展示：

- 起止时间
- 动作标签
- 置信度
- 状态，例如 predicted 或 reviewed
- team side
- 已知时的球衣号
- 来源模型版本

MVP 的球员统计应先限制为按球员身份聚合的动作计数。

建议的统计分组：

- 按球衣号统计
- 按动作类型统计
- 无法归属到球员的 `Unknown` 桶
- 队伍级总计，用于和已归属总计对比

除非另一个 Lane 提供可审计的事件结果和阵容上下文，否则这版 MVP 不应声称能稳定给出 ace rate、attack success rate、playing time 这类高级结果统计。

### 5.6 导出中心

目的：

- 输出可机器读取的结果，并带上 provenance。
- 让用户清楚知道当前导出的是哪份复核或评估产物。

必须支持：

- 导出 `events.json`
- 导出 `events.csv`
- 展示导出时间
- 展示产物来源和 schema 版本
- 重新导出时不修改底层已复核结果

## 6. 工作流状态模型

即使后续存储层变化，产品也需要明确的 UI 状态。

建议的任务级状态：

| 状态 | 含义 | 进入条件 | 离开条件 |
| --- | --- | --- | --- |
| `draft` | 任务壳存在，但还没有校验过的源数据 | 创建任务 | 开始导入或删除任务 |
| `importing` | 正在挂载或检查源文件 | 开始导入视频或标注 | 导入成功或失败 |
| `ready_for_review` | 输入已校验，可准备复核产物 | 校验通过 | 开始复核 |
| `reviewing` | 操作员正在复核标签或预测 | 进入复核工作区并有待处理变更 | 复核批次完成或取消 |
| `review_complete` | 复核产物已经保存 | 复核结果已应用或确认 | 开始评估或导出 |
| `running` | 模型推理或评估正在进行 | 开始执行 | 结果成功或失败 |
| `results_ready` | 事件输出已生成 | 推理产物写出 | 开始评估或导出 |
| `evaluation_ready` | 评估输入已具备 | 复核或推理产物满足条件 | 开始评估 |
| `evaluated` | 评估产物已存在 | 指标报告写出 | 导出或重新评估 |
| `exported` | 至少一个导出产物已生成 | 导出成功 | 新一轮运行更新最新导出标记，但不删历史 |
| `failed` | 某个阶段失败，但可以恢复 | 任意阶段出错 | 用户重试或修改设置 |

建议的条目级状态：

| 状态 | 含义 |
| --- | --- |
| `source` | 来自导入标注或前序产物 |
| `predicted` | 来自模型推理 |
| `queued_for_review` | 已进入人工复核队列 |
| `reviewed_keep` | 确认但未改标签或时间 |
| `reviewed_relabel` | 人工改了标签 |
| `reviewed_moved` | 人工改了时间窗 |
| `reviewed_added` | 人工补了遗漏事件 |

这些状态只约束产品和 UX，不规定后续 lane 该用文件、SQLite 还是其他注册表实现。

## 7. 跨 Lane 接口契约

这一节定义其他 Lane 可以在内部怎么实现之前，必须对外提供什么。

### 7.1 导入与元数据契约

最小任务输入：

- 本地视频路径，或导入后的视频产物 ID
- 视频元数据：fps、duration、width、height
- 可选的标注清单路径，或导入后的标注产物 ID
- 可选的目标队伍上下文

对 product-frontend 而言，导入阶段必须能返回：

- 稳定源引用
- 校验成功或失败
- 可读的错误信息

这里不要求指定具体存储引擎。

### 7.2 复核契约

提供复核产物的 Lane 应暴露：

- 复核队列产物引用
- 复核结果产物引用
- 复核请求列表和 record index
- 每条变更都可审计的操作类型
- 应用结果前的源快照一致性保证

product-frontend 会把复核视为按契约非破坏式的流程。

### 7.3 推理与事件契约

模型或分析 Lane 应暴露：

- 采用当前事件 schema 的事件列表
- 事件背后的窗口证据，或同等可追溯依据
- 模型版本
- 每个事件的置信度
- 产物时间戳

前端不应假设身份补全一定存在。

### 7.4 评估契约

评估 Lane 应暴露：

- 指标摘要
- 逐类指标
- 混淆矩阵
- 数据集范围元数据
- 模型或权重 provenance
- 在需要时区分兼容性指标和严格指标

只要不是独立比赛切分，前端就必须能拿到明确警告。

### 7.5 身份补全契约

号码识别或身份识别 Lane 可以给事件补充：

- `team_side`
- `player_number`
- 可选 confidence
- 可选归属状态，例如 `assigned`、`unassigned`、`needs_review`

这版设计不决定算法、跟踪器或 OCR 内部实现。

### 7.6 存储与产物注册表契约

存储相关的 Lane 只需要保证：

- 稳定的产物引用
- 源产物不可变，或至少版本化
- 能按阶段列出任务最新产物
- 源、复核、评估和导出之间可追溯

这版设计不决定 SQLite、平面文件、嵌入式数据库还是其他实现。

### 7.7 导出契约

导出 Lane 应暴露：

- 导出产物路径或 ID
- 导出 schema 版本
- 源事件产物引用
- 导出时间戳
- 格式类型，例如 JSON 或 CSV

前端在下载或打开文件夹前，应先展示导出 provenance。

## 8. 验收标准

只有下面这些都成立，这个 MVP 才算可接受。

### 8.1 工作流验收

- 用户能从本地比赛视频创建一个分析任务。
- 导入错误要尽早阻断流程，并明确指出阻塞原因。
- 后续每个页面都能看出前置产物是否存在。
- 某一阶段失败后，可以重试而不丢失之前成功的产物。

### 8.2 复核验收

- 复核不会原地覆盖原始标注清单。
- 每次确认都记录操作类型、源快照、确认后的时间、确认后的动作和复核备注。
- 产品能区分 imported、predicted、queued、reviewed 四类条目。

### 8.3 评估验收

- 评估视图能清晰展示七类严格指标。
- 如果展示兼容性指标，它们必须和严格指标分开标记。
- 当评估来自非独立的同场比赛数据时，UI 必须提醒。
- 报告要标明使用的具体模型或权重。

### 8.4 统计验收

- 产品能展示动作计数统计，而不强行要求完整结果追踪。
- 未能归属球员的事件必须仍然可见，并计入明确的 Unknown 桶。
- 队伍总计和已归属总计可以对比，但不能因此声称已经有完整战术统计。

### 8.5 导出验收

- CSV 和 JSON 导出应匹配当前事件契约。
- 导出 provenance 必须能识别源产物和模型版本。
- 重新导出不能破坏复核历史或评估历史。

## 9. 本 MVP 明确不做

以下内容在这一阶段不承诺：

- 自动球衣号码识别内部实现
- 身份跟踪内部实现
- 持久化存储引擎选择
- 完整球员档案
- 比赛数据库设计
- 结果级排球统计
- 多用户协作
- PDF 仪表盘等复杂报表

## 10. 仍需用户确认的选择

这次审计留下 4 个会明显影响后续实现的产品选择：

1. MVP 容器：
   本地浏览器应用，还是桌面壳层
2. 统计里未归属事件的展示：
   用显式 `Unknown` 桶，还是在球员表里隐藏但保留在队伍总计中
3. MVP 里“球员统计”的含义：
   仅动作计数，还是动作计数加人工录入的结果
4. 导出 schema 归属：
   直接把当前事件 schema 冻结为 `v1`，还是在其上再定义一层产品级 schema

建议默认值：

- MVP 先做本地浏览器应用。
- 保留显式 `Unknown` 桶。
- MVP 球员统计先限定为动作计数。
- 先把当前事件 schema 视为 `v1`，以后再考虑加包一层版本化封装。

## 11. 设计交付摘要

MVP 应该表现为一个引导式分析工作台，而不是完整体育平台。产品中心应当是可复核的分析任务。现有 CLI 命令和文件契约已经足够支撑导入、复核、评估、事件查看和导出，所以前端应先把这些阶段可视化、可审计，再往身份自动化和长期数据系统扩展。
