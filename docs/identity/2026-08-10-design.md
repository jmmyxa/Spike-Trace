# Player Identity And Jersey Number Design

Status: phase 1 audit and design only. No shared runtime code changes are included in this phase.

## Goal And Non-Goals

Goal:

- identify USA players in match video
- keep short-term player continuity across frames
- read jersey numbers from visible evidence
- expose stable, auditable identity outputs for later per-player action statistics

Non-goals for this phase:

- retraining or redefining the seven-class action model
- changing action labels, action windows, or action confidence
- guessing a jersey number when evidence is missing
- turning half-court crop priors into hard team identity truth

## Recommended Architecture

```text
video + match metadata + usa_side_segments
  -> person detection
  -> short-term tracking
  -> team classification (usa / opponent / unknown)
  -> multi-frame number OCR candidate extraction
  -> identity resolution against roster constraints
  -> human review when required
  -> identity_results.json
  -> optional event_assignments joined back to ActionEvent by time overlap
  -> downstream stats consume confirmed identities only
```

Recommended implementation location for a later phase:

- runtime code: `src/spiketrace/identity/`
- tests: `tests/identity/`

Phase 1 does not create those files.

## Input Contract

The identity pipeline should consume an immutable snapshot rather than reading action internals ad hoc.

```json
{
  "format_version": 1,
  "video_id": "usa-germany-2024-olympics",
  "video_path": "../USA vs Germany _ Men's Volleyball _ Full Match _ 2024 Olympics [ylqePmC_klo].mp4",
  "video_sha256": "optional-but-recommended",
  "metadata": {
    "fps": 30.0,
    "width": 1280,
    "height": 720,
    "duration_seconds": 7687.333333333333
  },
  "target_team": "USA",
  "roster": [
    {
      "player_ref": "usa:08",
      "number": "08",
      "display_name": "optional"
    }
  ],
  "usa_side_segments": [
    {
      "segment_id": "set_1",
      "start_seconds": 74.0,
      "end_seconds": 1504.0,
      "usa_side": "far",
      "crop": [0, 0, 1280, 430],
      "boundary_tolerance_seconds": 1.0,
      "boundary_semantics": "inclusive_candidate"
    }
  ],
  "action_events": [
    {
      "event_id": "evt_000123",
      "start_ms": 12400,
      "end_ms": 14100,
      "action": "serve",
      "confidence": 0.91
    }
  ]
}
```

Contract rules:

- time must be preserved in source-video coordinates
- frame boxes use source-frame pixel coordinates as `[x1, y1, x2, y2]`
- `action_events` may be empty; identity processing must still work
- roster numbers should be strings to preserve leading zeroes and future special numbering rules
- segment provenance must pass through unchanged

## Output Contract

Identity output should be written separately from `events.json`, then optionally joined downstream.

```json
{
  "format_version": 1,
  "video_id": "usa-germany-2024-olympics",
  "run_id": "identity-2026-08-10T12-00-00Z",
  "target_team": "USA",
  "tracks": [
    {
      "track_id": "trk_000042",
      "start_ms": 12400,
      "end_ms": 14100,
      "team": "usa",
      "team_confidence": 0.94,
      "identity_ref": "usa:08",
      "identity_status": "confirmed",
      "number": "08",
      "number_status": "confirmed",
      "number_confidence": 0.88,
      "visibility_state": "back_only",
      "evidence_frames": [
        {
          "frame_index": 376,
          "timestamp_ms": 12533,
          "box_xyxy": [10, 20, 100, 260],
          "view": "back",
          "ocr_text": "08",
          "ocr_confidence": 0.92
        }
      ],
      "review_status": "not_required",
      "model_versions": {
        "detector": "pending",
        "tracker": "pending",
        "ocr": "pending",
        "resolver": "pending"
      }
    }
  ],
  "event_assignments": [
    {
      "event_id": "evt_000123",
      "track_id": "trk_000042",
      "identity_ref": "usa:08",
      "assignment_status": "confirmed",
      "overlap_ms": 1700,
      "assignment_confidence": 0.86,
      "evidence_track_ids": ["trk_000042"]
    }
  ]
}
```

Enum recommendations:

- `team`: `usa | opponent | unknown | out_of_scope`
- `identity_status`: `confirmed | candidate | unresolved | rejected`
- `number_status`: `confirmed | candidate | unreadable | not_visible | not_run`
- `review_status`: `not_required | pending | confirmed | rejected`

Contract rules:

- `track_id` is run-local and short-lived
- `identity_ref` is the stable identity key and must not be inferred from `track_id`
- candidate values must be stored as candidates plus evidence, not silently copied into confirmed fields
- downstream stats must treat only `identity_status=confirmed` as factual
- one action event may overlap zero, one, or many tracks
- a single canonical actor per event must not be emitted until product confirms the primary-actor rule

## Processing Rules

### Team classification

- Start with confirmed `usa_side_segments` as a search prior.
- Combine crop position, appearance, number candidates, and temporal continuity before deciding `usa`, `opponent`, or `unknown`.
- A player inside the USA crop must not automatically become `usa`.
- Segment boundaries and side-switch transitions default to `unknown` until evidence is re-established.

### Tracking and re-linking

- `track_id` is valid only inside one pipeline run.
- Short occlusions may reconnect if spatial continuity and appearance similarity both pass threshold.
- When reconnection is not strong enough, end the old track and start a new one.
- A later resolver may map multiple tracks to the same `identity_ref`, but the merge evidence must remain auditable.

Recommended starting product parameter:

- maximum temporary occlusion gap: `1.0` second

### Back-facing, front-facing, and unreadable numbers

- Treat front and back views as separate evidence types.
- Prefer clear back-number evidence over weak front-number evidence.
- Never guess a number from posture, role, or crop alone.
- When number evidence is absent or unclear, output `not_visible` or `unreadable`.

Recommended visibility states:

- `visible_clear`
- `visible_blurred`
- `occluded`
- `back_only`
- `front_only`
- `not_visible`

### Multi-frame OCR and roster resolution

- Run OCR only on frames that pass clarity, size, and pose thresholds.
- Preserve raw OCR text, normalized candidate text, confidence, and crop evidence.
- Aggregate across frames into ranked candidates.
- Final candidates must belong to the supplied roster.
- Concurrent on-court USA numbers must remain unique unless roster data explicitly allows an exception.
- If candidates conflict, downgrade to `candidate` or `unresolved` and route to review.

### Joining identity back to action events

- The action model remains the owner of action class, window boundaries, confidence, and model version.
- The identity layer reads action events but does not rewrite them.
- `event_assignments` should be derived from time overlap, spatial relation, and team status.
- Action predictions must not be used as a shortcut for guessing jersey numbers.

## Human Review Gates

The pipeline must create review items for at least these cases:

- team is not confidently `usa`
- multiple number candidates without a clear winner
- recognized number not in roster
- re-linked tracks after occlusion
- same-number conflict
- action event overlaps multiple plausible USA tracks
- segment boundary or side-switch vicinity
- OCR sees only one digit or low-confidence characters
- back-facing or occluded player without readable evidence

Review outputs should capture:

- `track_id -> identity_ref` or rejection
- confirmed or rejected number
- effective time span
- rejection reason
- evidence frame references
- reviewer and review timestamp

Review records should be immutable and versioned separately from raw action labels.

## Metrics

Identity metrics must be reported on a dedicated identity annotation set, isolated by match. The current 90-window same-match training manifest is not an acceptable formal validation set.

Recommended metrics:

- frame-level jersey number exact accuracy
  - exact match on frames marked readable with number truth
- frame-level character accuracy
  - optional supporting OCR metric
- track-level jersey number exact accuracy
  - exact match on tracks with enough readable evidence
- end-to-end identity accuracy
  - `identity_ref` and number both correct on evaluable USA tracks
- USA classification precision, recall, and F1
  - especially USA precision to avoid polluting player stats with opponent tracks
- tracking metrics
  - IDF1, HOTA, MOTA, ID switches, fragmentation, occlusion recovery rate
- action-to-player assignment accuracy
  - correct primary actor on events where a primary actor is defined
- coverage metrics
  - fraction of tracks and events that end in `confirmed`
  - fraction routed to manual review
  - fraction left unresolved

Reporting rule:

- unresolved or not-visible cases should be counted separately from wrong guesses
- coverage and accuracy must both be reported, because a conservative system can look accurate by refusing to answer

## Boundary With Other Systems

### Action model boundary

Owned by action model:

- action labels
- event windows
- event confidence
- action model version
- window-level evidence

Owned by identity layer:

- player detections
- track continuity
- team classification
- jersey OCR candidates
- `identity_ref`
- review routing and evidence
- event-to-player assignment outputs

### Data platform boundary

Owned by data platform:

- official roster and stable player keys
- lineup and substitution truth if available
- review storage and approval flow
- downstream stats aggregation and exports

The data platform must not treat `candidate` or `unresolved` identity outputs as confirmed facts.

## Product Decisions Required Before Implementation

1. What is the official roster source, and what is the canonical `player_ref` format?
2. Are leading zeroes or special temporary numbers valid in product-facing outputs?
3. Can one action event have multiple credited players, or must the pipeline emit one primary actor?
4. What minimum thresholds define acceptable USA precision, number accuracy, and confirmed-coverage?
5. What is the allowed occlusion gap for track relinking, and can identity continue across segment boundaries?
6. How will the dedicated identity annotation set be created and split across train, validation, and test matches?
7. Which OCR engine and model licenses are acceptable for local use and future distribution?
8. Where will human review records live, and who is allowed to publish an override?
9. What stable key does the downstream stats platform want: `identity_ref`, `event_id + track_id`, or a new event-assignment key?

## Phase 1 Exit Condition

Phase 1 is complete when:

- the repository audit is documented
- the input and output contracts are defined
- manual review gates are listed
- identity metrics are specified
- system boundaries are explicit
- product decisions still required before implementation are written down

No runtime behavior change is part of this phase.
