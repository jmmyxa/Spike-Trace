# Spike-Trace 项目规划与开发上下文

> 文档状态：已确认的项目基线  
> 更新日期：2026-08-09
> 用途：保存产品决策、MVP 边界和技术路线，供项目成员及后续 AI 持续开发时使用。

## 1. 项目愿景

Spike-Trace 最终应成为一个可以持续升级的排球比赛视频分析软件，而不是一次性脚本。

用户导入一场排球比赛视频后，软件应识别我方球员的技术动作，将事件归属到球衣号码，并长期保存比赛、球员和统计数据。用户可以在软件中查看及修正数据，也可以导出 CSV、XLSX、JSON 或其他格式。

长期需要支持的主要指标包括：

- 发球成功率与发球得分率。
- 球员每场及每局得分。
- 球员上场时间。
- 得分来源，包括扣球、拦网和发球。
- 一传次数、一传到位率和一传等级。
- 扣球次数、扣球得分和扣球成功率。
- 按我方球衣号码汇总的单场及跨比赛数据。

## 2. 当前最重要的产品决策

第一阶段优先开发核心动作模型，应用界面、完整数据库、报表和账号等产品功能暂时后置。

MVP 的目标不是宣称已经实现高准确率全自动统计，而是跑通一个可训练、可推理、可评估的动作识别闭环：

```text
标注视频 -> 训练动作模型 -> 输入完整视频 -> 滑窗推理
         -> 合并动作事件 -> 输出时间戳、类别、置信度 -> 人工检查
```

动作模型必须能够通过新增标注数据继续训练和替换。模型输出需采用稳定的数据契约，避免后续加入号码识别、数据库或界面时推倒重做。

## 3. MVP 范围

### 3.1 MVP 必须完成

1. 读取常见格式的本地比赛视频。
2. 获取视频帧率、分辨率、时长等元数据。
3. 按固定长度及重叠比例生成视频片段。
4. 根据动作标注训练视频动作分类模型。
5. 对完整视频执行滑动窗口推理。
6. 将相邻、同类且满足阈值的窗口合并为动作事件。
7. 输出事件 JSON 和 CSV，至少包含动作类型、起止时间、置信度和模型版本。
8. 提供训练集、验证集指标和混淆矩阵。
9. 保存训练配置、标签表和模型权重，保证结果可以复现。

### 3.2 MVP 暂不要求

- 完整桌面端或 Web 端界面。
- 用户账号、云同步或多人协作。
- 正式比赛数据库和球员档案页面。
- Excel/PDF 报表排版。
- 全自动球衣号码 OCR 和跨遮挡身份重识别。
- 精确的换人、轮转和上场时间统计。
- 无人工确认即可用于正式技术统计的准确率。

这些功能属于后续产品阶段，但动作模型的输出格式需要为它们预留接口。

## 4. 第一版动作标签

建议第一版使用以下互斥标签：

| 标签 | 含义 | 第一版识别目标 |
| --- | --- | --- |
| `background` | 无目标动作、等待或普通移动 | 必须 |
| `serve` | 发球动作 | 必须 |
| `receive` | 我方直接接对方发球的第一次触球 | 必须 |
| `set` | 二传组织动作 | 必须 |
| `attack` | 扣球、吊球等进攻击球 | 必须 |
| `block` | 拦网动作 | 必须 |
| `dig` | 针对对方进攻击球的防守起球，不含拦网 | 必须 |

对方直接出界且我方没有触球时标为 `background`。非进攻 free ball 的我方首次触球暂标为 `background`，并在备注写 `free-ball`，等待后续单独确定标签口径。

以下结果不应在数据不足时强行合并到第一版动作分类器中：

- 动作是否直接得分。
- 一传是否到位。
- 扣球是否出界或被拦。
- 发球是否为 ACE。

上述结果往往需要更长时间上下文、球轨迹、比分变化或多个球员之间的关系。后续可使用独立结果模型或事件规则引擎判断。

## 5. 输入视频基线

第一版训练和验收应尽量控制视频条件：

- 固定或相对稳定的全场机位。
- 最低 1080p，推荐 50 或 60 FPS。
- 球网和双方半场大部分时间可见。
- 避免大量回放、特写、字幕遮挡和频繁剪辑。
- 训练集和验证集必须按比赛划分，不能把同一场比赛的相邻片段随机拆到两边，否则评估结果会虚高。

不同机位、分辨率和比赛级别应记录为数据集元信息，便于后续定位模型在哪些场景失效。

## 6. 标注规范

每条标注至少需要包含：

```csv
video_path,start_seconds,end_seconds,label,team_side,player_number,crop_x1,crop_y1,crop_x2,crop_y2,split
videos/match_001.mp4,12.40,13.20,serve,far,8,0,0,1280,430,train
videos/match_001.mp4,16.20,17.00,receive,far,3,0,0,1280,430,train
videos/match_010.mp4,28.50,29.30,attack,near,12,0,170,1280,720,val
```

其中 `team_side` 和 `player_number` 可以为空。`crop_x1` 至 `crop_y2` 用于保留目标球队半场，四项应全部填写或全部留空。真实视频验证表明，同一全场画面可能同时出现我方拦网和对方扣球，因此首版训练应优先使用我方半场裁剪，并将动作中心放在约 0.8-1.0 秒窗口内。

标注时需要统一动作起止边界：

- 发球：从明显准备动作开始，到击球后的随挥结束。
- 接发球：从球员响应对方发球开始，到第一次触球后的动作恢复。
- 防守起球：从球员响应对方进攻开始，到触球后的动作恢复；拦网触球仍归 `block`。
- 二传：从准备触球开始，到传球动作结束。
- 扣球：从助跑或明显起跳准备开始，到落地或随挥结束。
- 拦网：从移动并准备起跳开始，到落地结束。
- 同一片段中存在多个主要动作时，第一版优先切成较短的单动作片段。

必须包含足够多的 `background` 负样本，包括普通跑动、庆祝、暂停、捡球和裁判画面，否则模型会过度报出动作。

## 7. 模型与推理架构

### 7.1 第一版模型

动作模型采用可插拔双路径，先复用公开模型验证可迁移性，同时保留自主训练能力：

- 自训练基线：`R3D-18`，结构简单，便于持续吸收本项目的人工修正数据。
- 预训练候选：直接加载六类 YOLO 排球动作权重，将 `spike` 映射为 `attack`，忽略 `ball`；不复制第三方仓库代码。
- 后续候选：VideoMAE、SlowFast 或轻量级时序 Transformer。
- 预训练权重先在现有标注窗口上评估；当前外部 YOLO 入口不会扫描整场，只有召回率达到可用水平且补齐整场候选生成入口后，才能用于候选片段发现和预标注。
- 球员跟踪、我方身份和球衣号码识别仍不是动作分类 MVP 的硬依赖。

内部训练、清单和严格指标使用稳定七类契约：`background, serve, receive, set, attack, block, dig`。上游 YOLO 保持六类能力，不要求旧权重提供 `dig`。评估同时输出严格七类 `metrics`，以及仅为比较旧模型宽泛防守触球候选能力而将 `dig -> receive` 的六类 `compatibility_metrics`；兼容指标不能覆盖人工标签或作为七类部署成绩。所有路径仍需保留置信度、模型来源和检测证据，外部项目公布的指标不能代替本项目按完整比赛隔离的评估。

### 7.2 推理过程

1. 视频解码并按目标帧率采样。
2. 使用固定长度窗口，例如 32 帧或 64 帧。
3. 相邻窗口保持重叠，减少动作落在边界时的漏检。
4. 模型为每个窗口输出各动作类别概率。
5. 丢弃低于类别阈值或判断为 `background` 的窗口。
6. 合并时间相邻且类别相同的窗口。
7. 对持续时间过短的孤立结果进行过滤。
8. 输出最终事件及推理证据。

### 7.3 事件输出契约

```json
{
  "video_id": "match_001",
  "event_id": "evt_000123",
  "start_ms": 12400,
  "end_ms": 14100,
  "action": "serve",
  "confidence": 0.91,
  "team_side": null,
  "player_number": null,
  "status": "predicted",
  "model_version": "action-r3d18-v0.1",
  "source": "sliding_window"
}
```

后续号码识别模块只需补充 `team_side` 和 `player_number`，不应改变动作模型接口。

## 8. MVP 验收标准

程序链路验收和模型质量验收必须分开。

### 8.1 程序链路验收

- 能在目标设备上完成训练和推理命令。
- 对损坏视频、空标注和未知标签给出明确错误。
- 同一配置和模型权重产生可复现结果。
- 能生成合法的 JSON、CSV 和评估结果。
- 长视频处理过程可以显示进度，并允许失败后定位原因。

### 8.2 模型质量验收

- 使用从未参与训练的整场比赛作为验证集。
- 主要指标使用每类 Precision、Recall、F1 和混淆矩阵。
- 同时评估事件级指标，不能只报告片段分类准确率。
- 第一轮不预设不现实的高准确率目标；先建立基线，再根据真实数据确定目标。
- 重点观察 `attack` 与 `block`、`receive` 与 `set` 等易混类别。

## 9. 只统计我方和号码归属的后续方案

动作模型跑通后，再按以下顺序加入身份归属：

1. 检测球员、球网和场地，获得球员轨迹与所在半场。
2. 每局开始时由用户确认我方半场，换边后更新。
3. 使用人物跟踪维持短时间轨迹。
4. 从轨迹中选择号码清晰的正面或背面帧执行 OCR。
5. 对多帧识别结果进行置信度加权投票。
6. 将候选号码限制在赛前录入的合法名单中。
7. 使用场上人数、号码唯一性、轮转位置和自由人等阵容约束排错。
8. 将低置信度结果交给人工确认。

仅依靠逐帧 OCR 无法稳定完成号码归属。遮挡后的重新绑定还需要外观特征、位置连续性和阵容状态共同判断。

## 10. 长期产品数据架构

动作模型稳定后，软件采用本地优先的数据架构：

- SQLite 保存比赛、球员、阵容、轨迹、事件、审核记录和统计结果。
- 视频和证据片段保存在文件系统，数据库只保存路径、哈希和元数据。
- 原始预测与人工修正同时保留，不直接覆盖。
- 每条事件记录模型版本和置信度。
- 统计指标从事件数据重新计算，而不是只保存不可追溯的汇总数字。
- CSV、XLSX、JSON 和 PDF 是导出格式，不是内部唯一数据源。
- 后续可以提供项目归档格式，例如 `.spiketrace`，用于跨设备备份和恢复。

长期界面可包含比赛资料库、分析任务、校对工作台、比赛报告、球员档案、导出中心以及模型管理，但它们不属于当前动作模型 MVP。

## 11. 长期统计口径草案

以下定义需要在进入正式统计功能开发前由使用者最终确认：

| 指标 | 建议公式 |
| --- | --- |
| 发球成功率 | 发球进入有效回合次数 / 发球总次数 |
| 发球得分率 | ACE 次数 / 发球总次数 |
| 个人得分 | 扣球得分 + 拦网得分 + 发球得分 |
| 扣球成功率 | 扣球直接得分 / 扣球尝试次数 |
| 一传到位率 | 一传到位次数 / 有效一传次数 |
| 上场时间 | 球员进入场上至被换下的有效比赛时间累计 |

一传建议保留 0-3 级评分，而不只保存“到位/不到位”。对方失误得分原则上不归入任何我方球员的个人得分。

## 12. 推荐开发阶段

### 阶段 A：动作模型闭环，当前优先级

- 建立标注规范和数据集清单。
- 实现视频片段加载、训练、验证和整场推理。
- 建立 R3D-18 基线模型。
- 接入可选 YOLO 预训练动作检测器，生成兼容性指标和人工复核表。
- 输出动作事件 JSON/CSV。
- 已用真实比赛建立第一份同场零样本基线报告；独立验证基线仍待第二场比赛。

### 阶段 B：增强事件理解

- 加入球员、球和场地检测。
- 从动作分类升级到时序动作定位。
- 结合比分、球轨迹和动作顺序判断动作结果。
- 支持发球是否成功、扣球是否得分和一传等级。

### 阶段 C：我方与号码归属

- 球员跟踪、我方半场判断和换边处理。
- 多帧号码 OCR、轨迹绑定和阵容约束。
- 为低置信度身份提供人工确认。

### 阶段 D：完整软件产品

- 本地比赛资料库和数据库迁移。
- 视频校对工作台。
- 按比赛、局次和球员统计。
- CSV、XLSX、JSON、PDF 导出。
- 数据备份、恢复和模型升级。

2. 标记每局美国队位于近端或远端的时间范围，正确处理换边。
3. 加入至少一场独立比赛作为验证集；本场所有片段只能属于同一数据集分区。
4. 继续从完整回合补齐七类正样本；样本量和类别覆盖满足训练条件后，再决定微调外部权重还是训练
   R3D-18 基线。
5. 保留原始预训练权重、复核规格、人工结果和基线元数据，保证后续实验可复现。
6. 当前基线设备已记录为 Windows 11、Ryzen 7 9800X3D、61.7 GB 内存、CPU 推理且无
   可用 CUDA；换设备实验时继续记录相同信息。

首轮实验建议准备至少 3-5 场目标机位的完整比赛。少量数据可以验证流程，但不能
代表泛化能力；后续需要持续加入不同场馆、光照、球衣、机位和比赛水平的数据。

## 14. 给后续开发者和 AI 的约束

- 当前优先级始终是动作模型训练和推理闭环，除非项目负责人明确调整。
- 不要在缺少独立验证集时声称模型达到可用准确率。
- 不要用随机输出或基于文件名的假结果替代模型推理。
- 先保持模块化单体结构，不要过早引入微服务。
- 模型、事件规则、号码归属和统计公式必须保持独立边界。
- 新功能不得破坏事件输出契约；需要变更时应进行版本化。
- 训练/验证/测试集必须按比赛隔离。
- 所有模型结果必须保留置信度、模型版本和来源信息。
- 人工修正数据是未来训练集的重要资产，后续产品不得丢弃修正历史。
